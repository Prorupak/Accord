# Phase 05 — Authentication, authorization and security

**Status: Proposed.** This is a security contract for future Phase 05-I implementation. It is not a claim v0.1.0 has authenticated endpoints.

## Trust model

```
Untrusted browser input + cookie
      ↓
Next Node route → Better Auth verifies session → database verifies project ownership
      ↓                                               ↓
Strict request validation                    scoped, transactional Prisma calls
      ↓
Safe typed response (no audit content in logs)
```

A signed-in frontend component is **not authorization evidence**. Each protected server operation verifies a current session and scopes database reads/writes to the session user.

## Login scope

- Better Auth with email/password and DB sessions only. `User`, `Session`, `Account`, `Verification` should be generated by pinned Better Auth tooling, not handwritten from assumptions.
- Set `BETTER_AUTH_SECRET` and canonical `BETTER_AUTH_URL` as server-side runtime configuration. Use HTTPS, Secure cookies on HTTPS, HttpOnly where supported by the framework and appropriate SameSite policies.
- Allow trusted origins explicitly. Auth endpoints use Better Auth's CSRF/session protections; product cookie-mutating routes must independently reject foreign Origin and invalid JSON content type.
- Public signup must be **disabled by default** for a hosted deployment unless email ownership verification and recovery are added. `ACCORD_SIGNUP_ENABLED` needs a **server-side** toggle, not UI hiding alone.
- Phase 05-I deliberately excludes SMTP/email verification, password-reset delivery, OAuth, passkeys and SSO. Therefore a public self-serve registration flow is *not production-complete*. Document how self-hosters bootstrap initial accounts with an explicit temporary signup policy.
- Account lockout/rate limiting and session configuration must use supported Better Auth options; avoid inventing incompatible option keys.
- Session revocation must invalidate access to every project API; sign-out only hiding UI is insufficient.

## Authorization requirements

| Operation | Required condition | Response when blocked |
|---|---|---|
| List projects | Verified session; scope to `Workspace.ownerId = session.user.id` | `401` if signed out |
| Create project | Verified session; personal workspace created idempotently | `401`, or typed storage error |
| Get/rename/delete project | Verified session + ownership at database lookup | `404` for absent or other owner |
| Save snapshot | Same ownership + valid AuditV1 + expected version | `401` / `404` / `409` / `400` |
| Load snapshot | Same ownership; never fetch unrelated JSONB | `401` / `404` |
| Guest CSV workflow | No session required | Always works without DB |
| Existing FastAPI AI endpoints | Existing bounded public behavior preserved | Existing FastAPI error codes unchanged |

Never let the client specify `workspaceId` or `ownerId` to grant access. A route with a project UUID **must not** perform `findUnique({where:{id}})` and only then assume the caller may use its returned data. Scope via an authorized join/filter or a guarded consistent DB transaction. Project existence must not leak via error details or timing-sensitive extra response fields where avoidable.

## Security table

| Threat | Control | Test proof |
|---|---|---|
| Broken object-level authorization | Filter by session owner on every query | User A cannot list/get/rename/save/delete user B's project even with real UUID |
| CSRF | SameSite/Origin checks + Better Auth protections | Cross-origin POST rejected |
| Session replay | Server-side session revocation/expiry | Old cookie fails immediately after sign-out |
| Tampered audit | Replay/invariants checked server-side | Forged accepted pair/row reference rejected before DB write |
| Race or lost update | Version CAS + transaction + unique constraints | 2 saves same version → exactly 1 succeeds |
| Unbounded payload | Request body cap + strict AuditV1 | 413 with no DB write |
| Sensitive logging | No CSV/audit/token data in logs | Test redacted errors and failure traces |
| Cross-route auth bypass | Explicit Next/Vercel routing | Auth URL resolves to Next, not FastAPI |
| Signup abuse | Disabled default public signup; auth-specific controls | Signup endpoint denies registration when disabled |
| User enumeration | Generic login/reset messages; no public project existence | Invalid account/project errors do not reveal identity |

## Privacy and consent

Accord's current guest flow is browser-first. **Visiting `/`, importing CSVs or using guest export must not cause a persistence request.** On explicit Save, disclose that parsed source strings, mappings and the review/audit history go to the configured PostgreSQL database. The `audit.json` download itself contains source data. AI inference remains a separate, bounded transmission of limited data to the configured provider.

Do not claim persistence is zero-knowledge, encrypted end-to-end, or cryptographically proof of original file bytes. App-layer audit replay checks consistency, not authenticity of the stored original file hash.

## Implementation review checklist

1. Read `web/next.config.ts`, `vercel.json`, current FastAPI guard, `CLAUDE.md` and this file.
2. Inspect the installed Better Auth/Prisma docs and generate core auth schema; commit migration.
3. Ensure all sensitive modules have `server-only` import guard when supported; no client import of Prisma.
4. Test cross-user requests with a **real PostgreSQL** DB, not just mocked ownership helpers.
5. Test signed-out session, expired session, cookie revocation, bad origin and signup-disabled behavior.
6. Confirm responses and logs do not include email addresses, source cells, audit JSON, tokens or passwords.
7. Add production readiness limitations to deployment docs; no claims about account deletion or email verification until built.
